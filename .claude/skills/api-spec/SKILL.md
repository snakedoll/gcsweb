# API 명세 비교·작성

원칙: **비교 → 차이 보고 + 승인 요청(한 메시지) → 승인 1회 → 일괄 쓰기.** 승인 전에는 노션에 쓰지 않는다. 항목별로 따로 묻지 않는다. 노션 MCP는 `.mcp.json`의 `notion`(잇장 팀노션)을 쓴다.

- `check`: 보고만 하고 끝낸다. 승인 요청·쓰기 없음.
- `write`(기본): 보고와 승인 요청을 한 메시지로 내고, 승인되면 쓴다.

- API 명세서 DB: `3ba0e5a4-015e-801c-984c-d87d8db6afa0` (data_source `collection://b110e5a4-015e-8220-b10f-07e252eb3ba3`)
- 기능명세서 DB: data_source `collection://3bf0e5a4-015e-80a3-9e48-000b184f99aa`

## 1. 코드 읽기

대상 `app/api/**/route.ts`와 그 라우트가 쓰는 `lib/` 헬퍼에서 뽑는다.

- Method, URL(경로 파라미터는 `{name}`, 쿼리는 `?key={key}`)
- 권한: `requireAdmin()` / 세션 필요 / 게스트 토큰(`X-Guest-Token`) / 없음
- 요청: Query·Body 필드, 타입, 필수 여부, Zod 제약
- 응답: `apiSuccess` data 필드와 타입
- 실패: `apiErrors.*` / `apiError(status, code, ...)` 호출을 모두 찾아 상태 코드·에러 코드·조건 표로

## 2. 노션 명세 찾기

`notion-query-data-sources`(SQL)로 URL·기능명이 맞는 행을 찾고 `notion-fetch`로 본문을 읽는다. v1 행과 v2 행을 구분한다.

## 3. 보고 + 승인 요청 (한 메시지)

중간 진행 상황("코드 읽는 중", "노션 찾음" 등)은 보고하지 않는다. 아래 형식으로 **한 번만** 낸다.

```
### <METHOD URL> — 일치 N건 / 차이 M건 / 명세 없음

| # | 항목 | 노션 | 코드 | 반영안 |
|---|---|---|---|---|
| 1 | Body.quantity 필수 | 선택 | 필수 | 필수로 수정 |
| 2 | 409 OUT_OF_STOCK | 없음 | 있음 | 실패 표에 추가 |

판단 필요
- 3. <항목>: 명세는 A, 코드는 B. 기획 의도가 A라면 코드 수정 대상입니다. 어느 쪽으로 맞출까요?

→ "반영"이라고 하시면 1~2를 노션에 씁니다. 일부만이면 "2 빼고 반영".
```

- **일치하는 항목은 표에 넣지 않는다.** 차이 0건이면 "명세와 코드 일치" 한 줄로 끝낸다.
- 여러 라우트면 라우트별 제목 + 표, 승인 문구는 맨 끝에 한 번만.
- 명세 행이 없으면 표 대신 "새 행 추가: 기능명 / Method / URL / ver"를 한 줄로 쓰고, 본문은 승인 후 4단계 형식으로 작성한다.
- 비교 대상: 필드 누락·타입·필수 여부, 에러 케이스(양방향), 속성(구현/개발 현황, ver, Category, 우선순위).
- **판단 필요**로 분리하는 경우: 코드와 명세 중 어느 쪽이 맞는지 기획 의도에 달린 것(명세 = 기획 의도일 수 있음). 이것은 반영안을 쓰지 않고 질문만 한다.
- **v1 행은 수정하지 않는다.** v1 차이는 반영안에 "v2 행 신규(v1 복사) 후 v2에 반영"으로 적는다.

## 4. 승인 후 쓰기

- 승인된 항목만 한 번에 쓴다. 판단 필요 항목은 답을 받은 것만 포함한다.
- 새 행 속성: `기능`(예 `QRshop_주문 생성`, 도메인 접두사 통일), `Method`, `URL`, `Category`, `ver`, `구현`, `개발 현황`.

본문은 기존 행과 같은 형식을 따른다.

```
## 1. 개요
- 기능: …
- 엔드포인트: METHOD /api/v2/…
- 권한: …
## 2. 와이어프레임
- [화면 이름](Figma 노드 URL) …
## 3. 요청
- Query Parameters / Body Parameters 표 (필드명 | 타입 | 필수 여부 | 설명 | 제약 사항)
- 요청 예시 (JSON)
## 4. 응답
- 성공 (200 OK) 표 (필드명 | 타입 | 설명) + 성공 예시
- 실패 표 (상태 코드 | 에러 코드 | 설명) + 실패 예시
## 5. 비고
- 서버 계산 규칙, 트랜잭션, 프론트 표시 규칙 등
```

- 응답 형식은 `{ status, code?, message, data }`. 성공은 200, 409만 도메인 에러 코드, 메시지는 짧은 한글 명사구.

## 5. 완료 보고 (짧게)

```
반영 완료 2건
- <기능명> 수정: <행 URL>
- <기능명> 신규: <행 URL>
확인 필요: Assigned 지정(MCP로 불가), 기능명세서 '<행>' 상태 변경 여부
```
